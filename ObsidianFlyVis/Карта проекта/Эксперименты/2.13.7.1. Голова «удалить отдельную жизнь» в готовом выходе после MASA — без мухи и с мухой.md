# 2.13.7.1. Голова «удалить отдельную жизнь» в готовом выходе после MASA — без мухи и с мухой

Состояние: закрыт. Код: `life_filter_head_v1`.

Лучше ли муха выбирает отдельные ложные жизни для удаления, чем тот же фильтр без мухи?

runs/life_filter_head/report_dev.json; лог runs/life_filter_head_log.txt ([LIVES]). Жизни: train 196 216 (полностью ложных 5 143, с верной рамкой 15 339, без учитываемых 175 734; с меткой 20482), dev 49 652 (1 367 / 4 053 / 44 232), test 54 104 (1 523 / 4 130 / 48 451), val7 11 029 (242 / 947 / 9 840); рамок без однозначной жизни — train 64, dev 26, test 26, val7 0. AP на dev: без мухи 0.5801, с мухой 0.5800, разность -0.0001 [-0.0128; +0.0110]. Бюджет потерь 1 % на dev: без мухи (порог 0.7): ложных рамок убрано 419, верных 218, потеряно 17/2447, точность удаления 0.643; с мухой (порог 0.7): ложных рамок убрано 560, верных 273, потеряно 21/2447, точность удаления 0.641. test/val7 и HOTA не считались.

На уровне отдельной жизни муха не улучшает ранжирование ложных жизней: AP одинаков (−0,0001, ДИ содержит 0) — в отличие от цепочек, она и не ухудшает его. Наблюдение, не входившее в критерий: при бюджете 1 % на dev голова с мухой на том же пороге 0,7 удаляет больше ложных рамок (560 против 419) при немного больших потерях (21 против 17 объектов) — порог и бюджет выбраны на тех же данных, вывода из этого не делаю. Закрыт способ «сырые сигнатуры мухи в начале и конце жизни → линейная голова жизни»; версия «нужна история внутри жизни» не проверена. Найдена ошибка 09.10 (разбор автора): в signatures.npz один номер трекера встречается в нескольких записях жизней (трек потерян и вернулся с прежним номером; dev — 49 652 записи при 41 304 уникальных номерах, train — 196 216 при 159 592). Рамки выхода относились к жизни по номеру, а не по записи и интервалу кадров: метки и потери считались для объединения всех жизней номера (pos = {tid: i} оставлял последнюю запись), признаки life_features (уверенность, число строк) смешивали жизни номера, удаление шло по номеру. Пример: 019efe88-bbc2a4ac, номер 8 — жизни 0–129 (3 верных, 5 ложных) и 141–221 (0 верных, 8 ложных) получили общую метку 0. Ограничение вывода: опыт не является чистой проверкой способности мухи различать отдельные жизни (метки и признаки смешивали жизни одного номера); повтор — life_filter_head_v2.

Закрыта по заранее записанному критерию перехода (dev); test/val7 и HOTA не считались. Направление «удаление с мухой» по уровням цепочка → жизнь проверено при нынешних сигнатурах (только концы жизней) — сигнала нет. Оставшиеся версии из разбора 09.10: история мухи внутри жизни (новый проход FlyVis на GPU, контроль с той же историей без мухи) и обучаемое объединение — каждое по отдельному согласованию затрат.

Нельзя заявлять вклад FlyVis в выбор ложных жизней; наблюдение по бюджету (больше удалённых ложных рамок) не заявляется — порог выбран на тех же данных и не входил в критерий. Только dev. Числа получены с ошибкой идентификации жизней (см. interpretation) — как вердикт для отдельных жизней не использовать.
