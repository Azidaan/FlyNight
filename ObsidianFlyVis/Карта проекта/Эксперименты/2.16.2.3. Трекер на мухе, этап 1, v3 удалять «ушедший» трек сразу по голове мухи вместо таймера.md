# 2.16.2.3. Трекер на мухе, этап 1, v3: удалять «ушедший» трек сразу по голове мухи вместо таймера 30 кадров

Состояние: завершён с отрицательным результатом. Код: `fly_tracker_lifecycle_v3`.

Снижает ли раннее удаление «ушедших» по мухе переключения ID и даёт ли HOTA больше, чем по геометрии?

Пороги удаления (dev): геометрия 0.599, муха 0.613, вход + муха 0.543. ΔHOTA к стенду, test: геометрия -0,020 [-0,103; +0,052] (20/14); муха -0,015 [-0,073; +0,034] (21/12); вход + муха -0,016 [-0,089; +0,053] (15/19); IDSw 2221 → 2237 (муха). val7: геометрия -0,113 [-0,600; +0,172] (6/1); муха +0,063 [-0,040; +0,164] (5/2); вход + муха +0,259 [-0,023; +0,679] (5/2). Для сравнения v2 (без удаления): +0,08 на test.

Раннее удаление «ушедших» треков снимает выигрыш v2 (test +0,08 → ≈ 0) и не снижает переключения ID: ошибочные повторные захваты у ByteTrack редки, а каждый пятый «ушедший» по голове объект возвращается и получает новый номер. Муха и здесь не отличается от геометрии.

Оба критерия не выполнены → completed_negative. Удаление по голове — не рычаг; ветка «решения о жизни трека» на одной модели исчерпана: полезное действие (продолжение слабой детекцией) не требует мухи. Мухе нужны действия со спорными случаями (сшивка после долгого заслонения, ночное рождение) или дообучение (К1).

Что удаление по мухе бесполезно при другом пороге: проверен один порог (точность «ушёл» ≥ 0,8).
