## Интерпретация
Эта реализация (буфер потерянного трека 150 вместо 30 в ByteTrack, без мухи) не сработала: HOTA после MASA ниже на 0,33 по видео (ДИ ниже 0, лучше лишь в 4 видео из 35), без сшивки — ниже на 0,20; ночью так же. Узел провала (по разбору без сшивки, где действует только трекер): буфер закрывает часть длинных разрывов (31–150 кадров: 424 → 390), но долго потерянный трек подхватывает чужой объект — номеров, покрывающих несколько объектов разметки, 338 → 422, коротких разрывов 1 935 → 2 001 (объект, у которого номер «украден», рвётся заново). Повторное сопоставление ByteTrack для долго потерянного трека идёт только по IoU с прогнозом фильтра Калмана, без проверки внешности; через десятки кадров прогноз уходит, и совпадение по рамке перестаёт отличать свой объект от чужого (это объяснение механизма, прямой замер ухода прогноза не делался). Запас связей аудита (+1,33 по разметке) этой реализацией не взят.

## Решение
По порядку автора (11.10): действие не принесло пользы — А1 остановить; метку для срока > 30 кадров и сравнение голов с мухой и без не ставить, А3 не запускать. Замены узла (правило 6.15; только список, без запуска — решение автора): 1) повторное сопоставление долго потерянного трека по последней наблюдённой рамке вместо дрейфующего прогноза (OC-SORT, Cao et al., CVPR 2023 — observation-centric recovery); 2) проверка внешности для потерянных треков перед повторным сопоставлением (BoT-SORT, Aharon et al., 2022; Deep OC-SORT, Maggiolino et al., 2023 — порог косинусного сходства признаков ReID); 3) буфер, растущий с уверенностью и длиной трека, а не фиксированный (собственное предложение, источник не подобран). Дешевле всего 1): только трекер на процессоре, но сшивка MASA требует пересчёта сигнатур и эмбеддингов на GPU (~2,5 ч).

## Нельзя заявлять
Только dev 35 и один больший буфер (150); не исключено, что промежуточный буфер (45–60) нейтрален или полезен — не проверено. Голова пары MASA обучена на жизнях train при буфере 30. Механизм «прогноз уходит» — объяснение, не измерено.
