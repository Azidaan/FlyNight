# 🔴 Голова удаления цепочки после MASA: ранжирование (AP) и порог при одинаковом бюджете потерь — муха против контроля

Сначала дешёвая часть: признаки, метки, вероятности обеих голов и части проверки dev сохраняются на диск (runs/chain_filter_rank: chains.pkl, probs.npz, folds.json); по предсказаниям вне обучения (dev) и итоговых моделей (test, val7) — AP, точность удаления, удалённые ложные/верные рамки и потерянные объекты разметки — без оценщика, по правилу output_filter_oracle. Порог — на dev (вне обучения) при бюджете потерь B ∈ {0,5 %; 1 %; 2 %} объектов разметки с попаданиями: наибольшее число удалённых ложных рамок при потерях ≤ B. Затем полный пересчёт HOTA (TrackEval) только для выбранных порогов. Кривая по доле всех удалённых цепочек — вспомогательная (72 % цепочек test без учитываемых рамок). Признаки, голова, части проверки — те же, что в [chain_filter_fly_v1↗](obsidian://open?vault=ObsidianFlyVis&file=01%20%D0%9C%D1%83%D1%85%D0%B0%2F%D0%AD%D0%BA%D1%81%D0%BF%D0%B5%D1%80%D0%B8%D0%BC%D0%B5%D0%BD%D1%82%D1%8B%2Fchain_filter_fly_v1). scripts/chain_filter_rank.py.

## Вопрос
Лучше ли муха ранжирует цепочки для удаления, и даёт ли она больше HOTA при том же допустимом бюджете потерь объектов?

## Гипотеза
AP головы с мухой выше; при одинаковом бюджете потерь фильтр с мухой удаляет больше ложных рамок и даёт больше HOTA.

## Ожидалось (до прогона)
(1) test: AP с мухой − без мухи > 0, ДИ по видео > 0; (2) при бюджете B = 1 % (порог на dev): HOTA фильтр с мухой − фильтр без мухи на test > 0, ДИ по видео > 0; val7 — тот же знак. Фактические потери на test приводятся для обоих вариантов.

## Интерпретация
(1) Муха ухудшает ранжирование цепочек: на test AP −0,05, на val7 −0,09 (ДИ ниже 0), на dev вне обучения разницы нет — признаки мухи (ещё 1 292 столбца при ~4 500 цепочках с меткой в dev) не переносятся с dev на другие видео; вероятная причина — переобучение или сдвиг между наборами (не проверено). (2) При одинаковом бюджете потерь 1 % фильтр с мухой хуже фильтра без мухи: test −0,039 HOTA (ДИ ниже 0), val7 −0,054 (ДИ ниже 0); фактические потери на test с мухой 1,18 % (без мухи 0,80 %). (3) С ограничением потерь выигрыш фильтра без мухи мал, но устойчив: B 1 % — +0,128 HOTA по видео на test (ДИ выше 0, 32/35), +0,07 на val7; прирост теперь в DetA и AssA одновременно, потеряно 19 объектов из 2 366. Прежний +0,44 в [chain_filter_fly_v1↗](obsidian://open?vault=ObsidianFlyVis&file=01%20%D0%9C%D1%83%D1%85%D0%B0%2F%D0%AD%D0%BA%D1%81%D0%BF%D0%B5%D1%80%D0%B8%D0%BC%D0%B5%D0%BD%D1%82%D1%8B%2Fchain_filter_fly_v1) был получен ценой 6,8 % объектов. Реальная достижимая часть запаса оракула (+1,35) при безопасном пороге — около десятой.

## Решение
Оба критерия не выполнены: признаки мухи в этой голове вредят и ранжированию, и HOTA при равном бюджете потерь. Узел провала — представление мухи в голове цепочки (среднее и σ сигнатуры по концам жизней, 1 292 столбца на малой выборке), не действие. По правилу 6.15 — замены: (а) сжатое представление мухи (несколько итоговых чисел вместо 1 292 — например, голова «совпадение рамки» [stitch_realness_fly_v1↗](obsidian://open?vault=ObsidianFlyVis&file=01%20%D0%9C%D1%83%D1%85%D0%B0%2F%D0%AD%D0%BA%D1%81%D0%BF%D0%B5%D1%80%D0%B8%D0%BC%D0%B5%D0%BD%D1%82%D1%8B%2Fstitch_realness_fly_v1), где муха давала +0,029 AP, как один признак); (б) больше данных для обучения головы — цепочки train 130 (нужна сшивка на train); (в) более устойчивая модель (регуляризация по группам признаков). Фильтр без мухи с бюджетом 1 % — рабочее улучшение носителя (+0,13 HOTA), не решение проблемы FlyVis. Переход к другой цели головы или архитектуре — после выбора автора.

## Нельзя заявлять
Нельзя заявлять вклад FlyVis в удаление цепочек; нельзя заявлять, что фильтр реализует заметную долю запаса оракула при безопасном пороге (≈ 10 %). test — из обучающей части BDD100K; val7 — 7 видео.
