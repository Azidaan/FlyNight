# 🟢 Мишень фовеального входа мухи на 30 Гц: может ли поправка положения в области глаза изменить решения трекера (оракул, без GPU)

↑ [[01 Муха/Темы/Прочее о мухе|Прочее о мухе]] · **Исход:** положительный · `fovea_target_30hz_v1`

Решение автора 11.10: кандидат «фовеальное считывание движения» отложен; перед возвращением — одна исправленная проверка мишени без GPU в действующем режиме 30 Гц. Вопрос: есть ли случаи потери или неверного сопоставления, где поправка положения в доступной области фовеального глаза могла бы изменить решение трекера, и какой узел фовеального входа тогда меняется. Область глаза — как в tracking/foveated_eyes.crop_box: квадрат со стороной max(2 · max(w, h), 64 px) вокруг прогноза рамки, сдвинутый внутрь кадра; в стенде глаз есть только у ведомых треков (при потере удаляется — scripts/build_fly_signatures.py). Оракул (разметка — только диагностика): перед первым сопоставлением ByteTrack прогноз центра трека заменяется центром уверенной детекции его собственного объекта разметки, если её центр внутри области глаза; объект трека — объект его последнего наблюдения (детекция → объект: венгерское внутри класса, IoU ≥ 0,5, интерполяция разметки между размеченными кадрами, как в [association_log_v1↗](obsidian://open?vault=ObsidianFlyVis&file=01%20%D0%9C%D1%83%D1%85%D0%B0%2F%D0%AD%D0%BA%D1%81%D0%BF%D0%B5%D1%80%D0%B8%D0%BC%D0%B5%D0%BD%D1%82%D1%8B%2Fassociation_log_v1)). O1 — только ведомые треки (нынешняя область глаза); O2 — также потерянные (узел «глаз сохраняется при потере»). Трекер стенда на сохранённых детекциях dev 35 (процессор); выход — scalabel на опорных кадрах, HOTA по TrackEval. scripts/fovea_target_30hz.py.

## Вопрос
Есть ли на 30 Гц запас HOTA от поправки положения в области фовеального глаза — для ведомых треков (O1) и при сохранении глаза на время потери (O2)?

## Гипотеза
Часть потерь и неверных сопоставлений вызвана уходом прогноза при том, что своя детекция видна в области глаза; идеальная поправка положения их исправляет.

## Ожидалось (до прогона)
Критерий (до прогона, не меняется): O1 — общий прирост HOTA (pooled) ≥ +0,3 и ДИ средней по видео парной разности > 0; то же отдельно для O2. Две величины показываются раздельно; ДИ относится к средней по видео разности, не к общему приросту. Формулировка итога (дописано до результата, 11.10): порог +0,3 — правило расходования ресурсов, а не доказательство отсутствия мишени; при непрохождении — «запас не достиг принятого порога для продолжения; кандидат откладывается», не «мишени нет». Измеряется запас от идеализированного выбора собственной уверенной детекции и сдвига прогноза к её центру в области глаза (размер рамки прежний; слабые детекции, случаи без своей детекции и иные поправки не рассматриваются) — конкретный оракульный сценарий, а не строгий потолок любой фовеальной поправки. Принадлежность детекций на промежуточных кадрах — по линейно интерполированной разметке (реальная — только на опорных кадрах); при перекрытии и резком движении интерполяция может ошибаться. O2 моделирует только возможность поправить положение потерянного трека; FlyVis в опыте не работает — способность сохранённого состояния мухи взять этот запас не проверяется. Счётчик changed в выходе — «число поправок для пар, не проходивших порог первого сопоставления до вмешательства» (стоимость ≥ 0,8), а не число фактически изменённых назначений. Сверка: без оракула — выход стенда (HOTA без сшивки 61,336, runs/class_gate/report.json).

## Интерпретация
Для нынешней области глаза (только ведомые треки, O1) запас от идеализированной поправки положения не достиг принятого порога для продолжения: общий −0,04, по видео −0,003 с ДИ через 0; ночью в среднем даже ниже (−0,26, ДИ через 0). Для узла «глаз сохраняется при потере» (O2) запас достиг порога: общий +0,47, по видео +0,55 [+0,25; +0,89], лучше в 27 из 35; прирост — через связывание (AssA 62,91 → 63,65, IDSw 1 990 → 1 865); ночью +0,28 с ДИ через 0. Поскольку O1 (та же поправка ведомых треков) сам по себе не даёт прироста, прирост O2, по-видимому, создают поправки потерянных треков (1 177 поправок для пар, не проходивших порог до вмешательства) — это вывод по разности вариантов, отдельно не измерен. Это запас при идеализированном выборе собственной уверенной детекции (по интерполированной разметке) и сдвиге прогноза к её центру, а не результат мухи: FlyVis в опыте не работает, и способность сохранённого состояния мухи найти такую поправку не проверена. Небольшой минус O1 указывает, что сам оракульный сценарий неидеален (размер рамки прежний, ошибки интерполяции, конкуренция треков).

## Решение
По критерию O2 — основание рассмотреть конкретный узел FlyVis: сохранение фовеального глаза (состояния мухи) на время потери трека и поправку положения потерянного трека по его сигналу. Следующий шаг — по правилу 6.16 одна рабочая версия с заранее записанным критерием и тем же вариантом без мухи (например, та же поправка по DIS или по внешности в области глаза) — только по решению автора; GPU — по отдельному согласованию. Для нынешней области глаза (O1) запас не достиг порога — этот сценарий откладывается.

## Нельзя заявлять
Нельзя заявлять пользу фовеальной мухи: опыт оракульный, муха не работала. Нельзя заявлять, что поправка ведомых треков бесполезна вообще — проверен один идеализированный сценарий; порог +0,3 — правило расходования ресурсов. Ночной запас O2 не подтверждён (ДИ через 0). Только dev 35; принадлежность на промежуточных кадрах — по интерполированной разметке.
