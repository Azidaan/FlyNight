# Инструкция: как вести записи в плане и в графе

Этот файл написан вручную и генератором графа **не перезаписывается** (генератор трогает только файлы из своего списка `.generated.json`). Правила здесь — сводка действующих правил проекта: `AGENTS.md` (корень проекта), раздел 6 «Методические правила» в `dissertation/ЕДИНЫЙ_ПЛАН.md` и решения автора, принятые по ходу работы. Если правило меняется — меняется и этот файл.

---

## 1. Где что лежит и кто главный

| что | роль | правится |
|---|---|---|
| `dissertation/ЕДИНЫЙ_ПЛАН.md` | **главный документ**: полная хроника, все числа, решения, правила, планы | руками / скриптами агента |
| `experiments/project_history.json` | каталог карточек экспериментов (что ожидали, что получили, критерии, источники); из него генератор строит карточки и цвета графа | агентом по правилам раздела 3 |
| `experiments/metrics_glossary.json` | словарь метрик и терминов | до первого использования метрики |
| Git (origin gitlab) | факты о коммитах | коммит + push после каждого шага с зелёными проверками |
| `ObsidianFlyVis/` (этот граф) | **витрина**: понятная навигация по завершённому, планам и проблемам мухи | **только генератором** `scripts/build_obsidian_vault.py` (+ этот файл) |
| `runs/` | артефакты прогонов (JSON, логи) — на них ссылаются карточки | не затирать, не удалять |

Главное различие: **в план вносится всё, в граф — только итоги.** Граф — производное от плана и каталога; правка заметки графа руками пропадёт при следующей пересборке.

## 2. Единый план (`ЕДИНЫЙ_ПЛАН.md`)

### 2.1. Что вносить
**Каждый шаг — «каждый пчих»**: запуск, постановка, критерии, пробный прогон, найденная ошибка, поправка к собственному прошлому выводу, промежуточный результат, решение автора, отказ от шага и причина. Отрицательный результат вносится так же полно, как положительный (с числом, порогом и причиной — правило 6.10).

### 2.2. Журнал изменений (раздел `## Журнал изменений`, внизу)
- Новая запись — **сверху** журнала (сразу под заголовком).
- Только о **фактически сделанном и проверенном**.
- Формат заголовка записи: `**ДД.ММ.ГГГГ, ЧЧ:ММ MSK** — тема` (время московское).
- Подзаписи: `*ЧЧ:ММ, тема.* текст`; подзапись другого дня — `*ДД.ММ, ЧЧ:ММ, тема.* текст`.
- Типовая структура записи об эксперименте: *Постановка.* → *Получено (`id_карточки`).* → *Вывод.* → *Решение.*
- Hash коммита — в обратных кавычках: `` `4690dad` ``. Id карточки — тоже в обратных кавычках.
- Каждое число — с источником (путь к JSON/CSV в `runs/` или `experiments/`).
- Дробные числа в тексте — через запятую (8,26 px), знак минус — «−».

### 2.3. Остальные разделы
- Раздел 3 — все измеренные числа с адресом первичной таблицы.
- Разделы 4/5 — что закрыто (и по какому критерию) / что живо.
- Раздел 6 — методические правила; новое правило добавляется, когда ошибка «куплена» (6.12, 6.13, 6.14 …).
- Раздел 7 — действующий план: 7.6 кандидаты К (отбор по RPM), 7.7 проверки Д, 7.8 этапы трекера на мухе. Таблица идей `| К1 | название | основание | …` — из неё генератор строит блок «Запланировано».
- Пересмотр плана — только с согласия автора.

## 3. Карточка эксперимента (`experiments/project_history.json`)

1. **Каждый эксперимент — карточка** в `experiments[]`: обязательны `id`, `title`, `area` (id из `areas[]`), `state`.
2. **Состояние — одно из десяти:** `planned`, `ready`, `running`, `completed_positive`, `completed_negative`, `inconclusive`, `closed`, `infrastructure`, `superseded`, `unknown`. Отрицательный итог — `completed_negative`; закрытое по заранее записанному критерию направление — `closed`.
3. **До прогона** пишутся `question`, `hypothesis`, `expected` и `acceptance[]` (`{"criterion", "met": null}`). Критерий, дописанный после пробы, но до основного прогона, помечается как дописанный и с причиной.
4. **После прогона** — `done`, `obtained`, `interpretation`, `decision`, `cannot_claim`; `met` → `true`/`false` с `evidence`. Невыполненный критерий не удаляется.
5. **Только подтверждённое:** поле без источника остаётся пустым. Догадка в поле — нарушение.
6. **Каждое число — с адресом:** минимум — в тексте `obtained` рядом с путём к файлу; для ключевых чисел по возможности поле `metrics[]` (`{"key", "value", "baseline", "subset", "source", "locator"}`, `key` — из словаря метрик), его сверяет валидатор.
7. **Даты** — `ГГГГ-ММ-ДД` (`"started": "2026-10-06"`).
8. **Коммиты** в `commits[]` — только настоящие hash.
9. **Доказательства — ссылками**, не копиями: раздел плана, JSON, каталог `runs/`.
10. **Метки (`tags`)** связывают карточку с графом: `K1` … `K15` — идея из 7.6; `fundamental-D…` — проверка из 7.7; `fly-problem-P2` — проблема мухи.
11. **После любой правки каталога или словаря — проверка:**
    ```
    .venv/Scripts/python.exe scripts/validate_project_history.py
    .venv/Scripts/python.exe -m pytest tests/test_project_history.py -q
    ```
    Красный тест или FAIL — карточка не принята; исправляется каталог, а не тест.

## 4. Граф Obsidian (это хранилище)

### 4.1. Что попадает в граф
- **Только завершённые эксперименты и закрытие веток** — карточки с итоговым состоянием (`completed_positive`, `completed_negative`, `inconclusive`, `closed`, `superseded`) и записи журнала об итогах. Мелкие шаги (пробы, отладка) в граф не идут — они остаются в плане.
- **Запланированное и идущее** (`planned`, `ready`, `running` + идеи К/Д/этапы из разделов 7.6–7.8 плана) — отдельным **красным** блоком «09 Запланировано».
- **Проблемы мухи** P1–P11 — отдельным **красным** блоком «10 Проблемы мухи».
- Если неясно, является ли шаг итогом для графа, — агент спрашивает одной строкой в конце сообщения.

### 4.2. Блоки
| блок | содержимое |
|---|---|
| 00 Главная | вход |
| 01 Муха | понятия, хронология мухи, «что можно и нельзя заявлять», холст «Карта мухи», эксперименты мухи |
| 02 Эксперименты | завершённые карточки по направлениям |
| 04 Термины и метрики | из словаря |
| 05 План | разделы плана |
| 06 Журнал | записи журнала (итоги и закрытия), по дням |
| 07 Исследования | результаты глубоких поисков (`research_*`) |
| 08 Документы | прочие документы |
| 09 Запланировано | красный: планы, идущие эксперименты, идеи из 7.6–7.8 |
| 10 Проблемы мухи | красный → жёлтый → зелёный: P1–P11 |

Связи: блоки — деревья (структурные ссылки дают рёбра графа); перекрёстные ссылки — через `obsidian://open?vault=ObsidianFlyVis&file=…` (кликабельны, но ребра не создают), чтобы граф не превращался в клубок.

### 4.3. Цвета и перекраска
- **Идеи плана (блок 09)** — автоматически по меткам карточек: карточка с итоговым исходом → ✅ (зелёный, «выполнено»), `running` → 🔄 (жёлтый, «в работе»), нет карточки → ⏳ (красный, «открыто»). ✅ значит «сделано», а не «успешно» — исход смотреть в карточке.
- **Проблемы мухи (блок 10)** — вручную, после эксперимента, в `scripts/obsidian_fly_problems.py`, словарь `STATUS`:
  - 🔴 «открыта» — по умолчанию;
  - 🟡 «частично» — подтверждённый сдвиг, но критерий из заметки не достигнут;
  - 🟢 «решена» — критерий из заметки выполнен.
  К статусу — обоснование со ссылкой на карточку. Новые доказательства и смена «первого шага» — в `PROBLEMS[...]` того же файла (ссылки `{c:id}` на карточку, `{i:К1}` на идею, `{f:F18}` на тему исследования).
- Цвета графа — в `.obsidian/graph.json`. Obsidian перезаписывает этот файл, пока открыт: после пересборки — «Перезагрузить без сохранения».

### 4.4. Как обновлять
После каждого завершённого эксперимента или закрытия ветки:
```
.venv/Scripts/python.exe scripts/build_obsidian_vault.py
```
затем коммит вместе с планом и каталогом. Заметки, созданные генератором, руками не править — правка источника (план, каталог, `obsidian_fly_problems.py`, функция `build_fly` в генераторе) и пересборка.

## 5. Порядок работы над одним экспериментом

1. **Выбор** — по схеме RPM (arXiv 2608.13940): пул 10–15 кандидатов, попарное сравнение со ссылками на уже измеренные числа проекта, стоимость, достижимость; ранжирование — в план (7.6).
2. **Карточка `planned`/`running`** с `expected` и `acceptance` — **до** прогона; запись в журнал о постановке.
3. **Дешёвая проверка мишени** (правило 6.1) и пробный прогон кода; сверка реализации со стендом.
4. **Пилот на полных данных** (не на 2–3 видео); долгие расчёты — через `Start-Process`/`.cmd`, рядом с обучением — приоритет Idle; на Windows — один процесс CUDA или мьютекс `tracking/gpu_lock.py`.
5. **Итог** в карточку (`obtained`, `decision`, `met`), запись в журнал, при необходимости — статус проблемы мухи.
6. **Проверки** каталога (валидатор + тесты) → **пересборка графа** → **коммит и push**.
7. **Отчёт** автору: что сделано, чем доказано, в конце — сводка «эксперимент → метрика → % к baseline → доля измеренного потолка»; ноль — нулём.

## 6. Что спрашивать у автора, а что нет
- **Без спроса:** коммиты и push (часто, после каждого шага с зелёными проверками), пробы и пилоты, разрешённые планом, пересборка графа.
- **Спросить и ждать:** загрузка данных, дорогое обучение (часы–сутки GPU, например ступень 1 К1), пересмотр плана, всё, что может навредить. Главное правило — «не навреди»: ничего не удалять, `runs/` не затирать, чужие незакоммиченные правки не трогать.

## 7. Методические запреты (кратко; полностью — план, разделы 6 и 8)
- Сравнивать прогоны, отличающиеся ровно одним условием; контроль обязателен.
- Не объявлять прирост без разброса и доверительного интервала (бутстрэп по видео).
- Не переносить знак с коротких прогонов на полные.
- Проверки детектора — только на видео, которых он не видел (val), не на `runs/train_cache`.
- Отрицательные результаты не подавать как пункты новизны; сомнение в новизне — кратко в `cannot_claim`, работа не останавливается.
- В текстах не писать «трекинг на дороге»: BDD100K — источник данных, а не домен.
