# AGENTS.md — правила для любого агента в проекте E:\Dissertation

Этот файл самодостаточен. Если пользователь говорит «прочитай AGENTS.md» —
прочитать целиком и дальше действовать по нему без дополнительных вопросов.
Файла CLAUDE.md в проекте нет намеренно: правила подключаются явно, этой фразой.
Подробная пошаговая инструкция по ведению плана и графа с примерами —
`ObsidianFlyVis/ИНСТРУКЦИЯ — как вести записи.md`; при расхождении главный этот файл.

## 1. Что это за проект

Диссертация: устойчивый многообъектный трекинг на данных BDD100K MOT при слабом
освещении, пересвете, окклюзии и сложном фоне. BDD100K — источник данных, а не
домен: в текстах не писать «трекинг на дороге».

- **Стенд.** Детектор YOLO26s (`weights/baseline_seed42/best.pt`, обучен на 640,
  запуск на 960, conf 0,01) + трекер `XYWHByteTrack`; метрика — HOTA
  (TrackEval), разброс — парный бутстрэп по видео.
- **Предмет работы — модель зрения мухи FlyVis** (734 параметра, ансамбль
  `flow/0000/000–049`). Она остаётся предметом навсегда: её можно менять,
  дообучать, дополнять чужими модулями; новизна — в мухе. Минусы мухи
  ведутся как проблемы P1–P11 (`scripts/obsidian_fly_problems.py`).
- **Детектор не заморожен:** изменения детектора — отдельные эксперименты с
  карточкой; проверки детектора — только на видео, которых он не видел (val).
- Всё окружение (Python, пакеты, веса, кэши) — строго внутри `E:\Dissertation`.

Главный документ — `dissertation/ЕДИНЫЙ_ПЛАН.md`: хронология, все измеренные
числа, что закрыто и почему, методические правила ([раздел 6↗](obsidian://open?vault=ObsidianFlyVis&file=05%20%D0%9F%D0%BB%D0%B0%D0%BD%2F6.%20%D0%9C%D0%B5%D1%82%D0%BE%D0%B4%D0%B8%D1%87%D0%B5%D1%81%D0%BA%D0%B8%D0%B5%20%D0%BF%D1%80%D0%B0%D0%B2%D0%B8%D0%BB%D0%B0)), действующий план
([раздел 7↗](obsidian://open?vault=ObsidianFlyVis&file=05%20%D0%9F%D0%BB%D0%B0%D0%BD%2F7.%20%D0%94%D0%B5%D0%B9%D1%81%D1%82%D0%B2%D1%83%D1%8E%D1%89%D0%B8%D0%B9%20%D0%BF%D0%BB%D0%B0%D0%BD)) и запреты ([раздел 8↗](obsidian://open?vault=ObsidianFlyVis&file=05%20%D0%9F%D0%BB%D0%B0%D0%BD%2F8.%20%D0%97%D0%B0%D0%BF%D1%80%D0%B5%D1%82%D1%8B)). Они действуют для агента так же, как для автора.

## 2. Пять мест записи и их роли

| место | роль | кто и когда пишет |
|---|---|---|
| `dissertation/ЕДИНЫЙ_ПЛАН.md` | полная хроника: каждый шаг, все числа, решения, «Журнал изменений» | агент — после каждого фактически сделанного шага |
| `experiments/project_history.json` | каталог карточек экспериментов: ожидание, итог, критерии, источники, коммиты | агент — по правилам [раздела 3↗](obsidian://open?vault=ObsidianFlyVis&file=05%20%D0%9F%D0%BB%D0%B0%D0%BD%2F3.%20%D0%92%D1%81%D0%B5%20%D0%B8%D0%B7%D0%BC%D0%B5%D1%80%D0%B5%D0%BD%D0%BD%D1%8B%D0%B5%20%D1%87%D0%B8%D1%81%D0%BB%D0%B0) |
| `experiments/metrics_glossary.json` | словарь метрик и терминов | агент — до первого использования метрики |
| `ObsidianFlyVis/` | граф-витрина: итоги, планы, проблемы мухи | **только генератор** `scripts/build_obsidian_vault.py` (+ ручная инструкция) |
| Git (`origin`, GitLab) | факты о коммитах | агент — коммит и push после каждого шага с зелёными проверками |

**Главное различие:** в ЕДИНЫЙ_ПЛАН.md вносится **всё** («каждый пчих»); в граф — только
итоги. Граф — производное от плана и каталога: заметку графа руками не правят.

Каталог `project_history.json` читают генератор графа (карточки, цвета, статусы
идей и проблем) и валидатор (сверка чисел с источниками). Окно «История проекта»
(`scripts/project_history_window.py`, «Запусти меня») сейчас не используется;
код и тесты оставлены, но вести записи ради него не нужно.

## 3. Карточка эксперимента (обязательно)

1. **Каждый эксперимент — карточка** в `experiments[]`: обязательны `id`,
   `title`, `area` (id из `areas[]`; новое направление сначала туда), `state`.
2. **Состояние — одно из десяти:** `planned`, `ready`, `running`,
   `completed_positive`, `completed_negative`, `inconclusive`, `closed`,
   `infrastructure`, `superseded`, `unknown`. Отрицательный итог —
   `completed_negative`; закрытое по заранее записанному критерию — `closed`.
3. **До прогона:** `question`, `hypothesis`, `expected`, `acceptance[]`
   (`{"criterion", "met": null}`), `started` (`ГГГГ-ММ-ДД`), state `planned`/`running`.
   Критерий, дописанный после пробы, но до основного прогона, помечается
   «дописан до прогона» с причиной.
4. **После прогона:** `done`, `obtained`, `interpretation`, `decision`,
   `cannot_claim`; в `acceptance` — `met: true/false` с `evidence`.
   Невыполненный критерий не удаляется. Только подтверждённое: если
   подтверждения нет, поле остаётся пустым. Догадка — нарушение.
4а. **Исправление текста — без удаления прежнего** (решение автора 10.10). Если
   итоговое поле карточки (`summary`, `obtained`, `interpretation`, `decision`,
   `cannot_claim`) исправляется, прежний текст переносится в `revisions[]`
   (`{"date", "commit", "field", "old", "reason"}`) — вдруг исправление окажется
   ошибкой; граф показывает их блоком «Прежние версии». В журнале плана поправка
   пишется новой записью, старые записи не правятся. Восстановление из истории
   git — `scripts/recover_revisions.py`.
5. **Каждое число — с адресом источника.** Минимум — в тексте `obtained` число
   стоит рядом с путём к файлу (`runs/…/summary.json`) или ключом в нём. Число
   без источника не записывается. Поле `metrics[]`
   (`{"key", "value", "baseline", "subset", "source", "locator"}`) — по
   возможности, для ключевых итоговых чисел: валидатор сверяет его с
   источником.
6. **Метрика из `metrics[]` описана в словаре** `metrics_glossary.json`
   (`title`, `ru`, `better`; по возможности `full`, `unit`, `range`, `tool`,
   `caveat`, `source`); термины — в ветке `terms`.
7. **Связи с Git — только настоящими hash** существующих коммитов.
8. **Доказательства — ссылками, не копиями** (`evidence[]`: раздел плана, JSON,
   CSV, каталог `runs/`, коммит).
9. **Метки связывают карточку с графом:** `K1`…`K15` — идея из [раздела 7.6↗](obsidian://open?vault=ObsidianFlyVis&file=05%20%D0%9F%D0%BB%D0%B0%D0%BD%2F7.6.%20%D0%9E%D1%82%D0%B1%D0%BE%D1%80%20%D1%81%D0%BB%D0%B5%D0%B4%D1%83%D1%8E%D1%89%D0%B8%D1%85%20%D1%8D%D0%BA%D1%81%D0%BF%D0%B5%D1%80%D0%B8%D0%BC%D0%B5%D0%BD%D1%82%D0%BE%D0%B2%20%D0%BF%D0%BE%20%D1%81%D1%85%D0%B5%D0%BC%D0%B5%20RPM%2C%2003.10)
   плана; `fundamental-D…` — проверка из 7.7; `fly-problem-Pn` — проблема мухи.
10. **После любой правки каталога или словаря — проверка:**
    ```
    .venv/Scripts/python.exe scripts/validate_project_history.py
    .venv/Scripts/python.exe -m pytest tests/test_project_history.py -q
    ```
    Красный тест или `FAIL` — карточка не принята; исправляется каталог, а не тест.

## 4. Единый план: как заполнять

- **Что вносить:** каждый шаг — постановку, критерии, пробный прогон,
  найденную ошибку (в том числе в прошлых выводах), поправку собственного
  вывода, промежуточный и итоговый результат, решение автора, отказ от шага и
  причину. Отрицательный результат — так же полно (число, порог, причина).
- **Журнал** (`## Журнал изменений`, внизу файла): новая запись — сверху,
  только о фактически сделанном и проверенном. Заголовок
  `**ДД.ММ.ГГГГ, ЧЧ:ММ MSK** — тема`; подзаписи `*ЧЧ:ММ, тема.* текст`
  (другого дня — `*ДД.ММ, ЧЧ:ММ, тема.*`). Для эксперимента — блоки
  *Постановка.* → *Получено (`id`).* → *Вывод.* → *Решение.* Hash коммита и id
  карточки — в обратных кавычках. Числа — через запятую, со ссылкой на файл.
- **Разделы:** 3 — все числа с адресом первичной таблицы; 4/5 — закрытое (по
  какому критерию) / живое; 6 — методические правила (новое — когда ошибка
  «куплена»); 7 — действующий план (7.6 кандидаты К по RPM, 7.7 проверки Д,
  7.8 этапы трекера на мухе; из таблиц `| К1 | … |` строится блок
  «Запланировано» графа). Пересмотр плана — только с согласия автора.

## 5. Граф Obsidian (`ObsidianFlyVis/`)

- **Пересборка — после каждого итога, отрицательного тоже** (решение автора 08.10): неудачный тест — такой же глобальный результат, на него опираются при выводах.
- **Что попадает:** только завершённые эксперименты и закрытия веток
  (состояния `completed_*`, `inconclusive`, `closed`, `superseded`) и записи
  журнала об итогах. Мелкие шаги — только в план. Если неясно, итог ли это для
  графа, — спросить одной строкой в конце сообщения.
- **Красные блоки:** «09 Запланировано» (карточки `planned`/`ready`/`running`
  и идеи из 7.6–7.8 плана) и «10 Проблемы мухи» (P1–P11).
- **Перекраска:** идеи блока 09 — автоматически по меткам карточек (итог → ✅
  зелёный «выполнено», `running` → 🔄 жёлтый; ✅ значит «сделано», не «успешно»).
  Проблемы мухи — вручную в `scripts/obsidian_fly_problems.py`, словарь
  `STATUS`: «частично» (сдвиг подтверждён, критерий не достигнут) → 🟡,
  «решена» (критерий заметки выполнен) → 🟢, с обоснованием и ссылкой на
  карточку; новые доказательства — в `PROBLEMS[...]` (`{c:id}`, `{i:К1}`, `{f:F18}`).
- **Обновление:** после каждого итога —
  `.venv/Scripts/python.exe scripts/build_obsidian_vault.py`, затем коммит.
  Генератор пишет только свои файлы (`.generated.json`), ручные заметки не
  трогает. Цвета — `.obsidian/graph.json`; открытый Obsidian перезаписывает
  его — после пересборки «Перезагрузить без сохранения».

## 6. Порядок работы над экспериментом

1. **Выбор по RPM** (arXiv 2608.13940): пул 10–15 кандидатов, попарное
   сравнение со ссылками на уже измеренные числа проекта, стоимость,
   достижимость; ранжирование — в план.
2. **Карточка с критериями до прогона** + запись о постановке в журнал.
3. **Дешёвая проверка мишени** (правило 6.1), пробный прогон, сверка новой
   реализации со стендом (воспроизвести штатное число до сравнения).
4. **Пилот на полных данных**, не на 2–3 видео; контроль, отличающийся ровно
   одним условием; ступени с остановкой по заранее записанному критерию.
5. **Итог:** карточка → журнал → статус проблемы мухи → проверки каталога →
   пересборка графа → коммит и push → отчёт.
6. **Отрицательный итог — заменить узел, а не закрыть линию** (решение автора
   07.10, план, правило 6.15). Измерением найти, какой узел модуля отвечает за
   провал; выписать 2–3 замены из других работ (с источником) и проверить
   сначала дешёвую. В карточке писать «эта реализация не сработала, узел
   провала — …, замены — …». Слово «закрыто» — только для конкретной гипотезы
   по её заранее записанному критерию, не для направления целиком.
7. **Действие прежде диагностики** (решение автора 11.10, план, правило 6.16). Перед серией
   назвать одно действие, меняющее выход трекера, и заранее — какой результат сделает
   его полезным; диагностика — только если от её ответа зависит выбор реализации. На
   действие — не более 3–4 диагностик, затем рабочая версия с HOTA или запись, почему
   действие прекращено (4-я — лишь при найденной ошибке в данных/измерении). После
   реализации — стенд / тот же вариант без FlyVis / с FlyVis; выигрыш только без мухи —
   улучшение трекера-носителя, не результат линии FlyVis. Учитывать время до решения:
   три дешёвые проверки за день — нормально, диагностика на сутки без следующего
   действия — нет.

## 7. Разрешения

- **Без спроса:** коммиты и push (часто; после каждого шага с зелёными
  проверками; конкретные файлы, не `git add -A` по всему проекту; в конце
  сообщения коммита — строка соавторства агента), пробы и пилоты, разрешённые
  планом или автором, пересборка графа, правки кода и записей.
- **Спросить и ждать:** загрузка данных, дорогое обучение и долгие расчёты
  (часы–сутки GPU), пересмотр плана, всё, что может навредить.
- **Никогда без отдельного разрешения:** `reset`, `checkout`, `clean`,
  `stash`, `pull`, `fetch`, смена веток, удаление файлов и `runs/`,
  перезапись чужих незакоммиченных правок. Главное правило — «не навреди».

## 8. Чего не делать (методика)

- Не сравнивать прогоны, отличающиеся более чем одним условием; не объявлять
  прирост без разброса и доверительного интервала; не переносить знак с
  коротких прогонов на полные (план, [разделы 6↗](obsidian://open?vault=ObsidianFlyVis&file=05%20%D0%9F%D0%BB%D0%B0%D0%BD%2F6.%20%D0%9C%D0%B5%D1%82%D0%BE%D0%B4%D0%B8%D1%87%D0%B5%D1%81%D0%BA%D0%B8%D0%B5%20%D0%BF%D1%80%D0%B0%D0%B2%D0%B8%D0%BB%D0%B0) и 8).
- Не подавать отрицательные результаты как пункты новизны; не обосновывать
  новизну отсутствием публикаций; сомнение в новизне — кратко в `cannot_claim`,
  работа не останавливается.
- Не проверять детектор на `runs/train_cache` (эти видео в его обучении).
- Не запускать обучения, TrackEval и обработку видео ради интерфейса или
  каталога.
- Не вставлять текст из Git, плана или JSON в HTML без экранирования; не
  проверять пути через `startswith` — только `Path.resolve()` +
  `relative_to(E:\Dissertation)`.

## 9. Запуск расчётов (Windows)

- Долгие расчёты — через `Start-Process` или `.cmd`-файл (процессы,
  запущенные напрямую из сессии агента, могут гибнуть); рядом с обучением —
  приоритет Idle сразу при запуске.
- Несколько CUDA-процессов одновременно зависают: один процесс GPU или
  мьютекс `tracking/gpu_lock.py`. Следить за памятью GPU (12 ГБ): большие
  пакеты — порциями.
- Правки файлов скриптами — через файл (Write), не через heredoc bash: он
  портит обратные слэши и эмодзи.
- Долгий процесс показывает прогресс (`status.json` / строки с оценкой
  оставшегося времени); пользователь хочет видеть прогресс.

## 10. Как отчитываться

- **По вехам**, не по каждой команде: запуск и завершение долгого процесса,
  итог эксперимента, срабатывание точки остановки, коммит. Перед шагом —
  что будет сделано; после — что сделано и чем доказано (число из файла,
  путь, вывод команды).
- **Отчёт об эксперименте:** постановка в одной фразе → таблица чисел →
  вывод простыми словами → что нельзя заявлять → решение и что дальше
  (дорогие шаги — вопросом автору).
- **В конце каждого отчёта — сводка в процентах к baseline:** «эксперимент →
  метрика → % к baseline → доля измеренного потолка». Ноль писать нулём; если
  пересчёт невозможен — сказать почему.
- Ошибки в собственных прошлых выводах называть прямо и сразу исправлять в
  карточке и журнале.
- Простым языком, без лишней математики; русский язык.

## 11. Где что лежит

- `scripts/` — эксперименты (`fly_*`, `gate_*`, `d*_*`), генераторы графа
  (`build_obsidian_vault.py`, `obsidian_fly_problems.py`), валидатор.
- `tracking/` — муха (`flyvis_motion.py`, `retina.py`, `foveated_eyes.py`),
  трекеры, `gpu_lock.py`; рантайм FlyVis — `tools/flyvis-runtime`, модели —
  `runs/flyvis/results/flow/0000/<id>`.
- `runs/train_cache/<id>` (200 видео train: 130/35/35 train/dev/test,
  `selection.json`), `runs/video_rate/<id>` (val7) — кэши детекций, движения,
  выравнивания; `runs/fly_signatures*` — сигнатуры мухи.
- `research_*/` — результаты глубоких поисков (`СВОДКА.md`).
- `scripts/validate_project_history.py`, `tests/test_project_history.py` —
  проверка каталога (обязательна); `evaluation/project_history/`,
  `ui/project_history.html` — окно истории (сейчас не используется).
