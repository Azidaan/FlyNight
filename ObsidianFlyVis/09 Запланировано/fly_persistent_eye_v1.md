# ⚪ Модернизация FlyVis: фовеальный глаз сохраняется и обновляется при потере трека, его остаточный поток поправляет прогноз положения (одна рабочая версия)

↑ [[09 Запланировано/FlyVis — планы|FlyVis]] · **Исход:** запланирован · `fly_persistent_eye_v1`

Основание: [fovea_target_30hz_v1↗](obsidian://open?vault=ObsidianFlyVis&file=01%20%D0%9C%D1%83%D1%85%D0%B0%2F%D0%AD%D0%BA%D1%81%D0%BF%D0%B5%D1%80%D0%B8%D0%BC%D0%B5%D0%BD%D1%82%D1%8B%2Ffovea_target_30hz_v1) — оракул поправки положения потерянных треков в области глаза (O2) +0,471 общей HOTA, по видео +0,547 [+0,245; +0,887]; для ведомых треков (O1) запаса нет. Решение автора 11.10: одна рабочая модернизация узла «состояние глаза». Гипотеза (не доказана): непрерывное состояние FlyVis помогает оценивать поправку положения после потери трека. Изменение узла FlyVis: в стенде глаз удаляется, когда трек перестаёт быть ведомым (scripts/build_fly_signatures.py); в новой версии глаз потерянного трека остаётся и каждый кадр смотрит на вырезку вокруг прогноза фильтра (tracking/foveated_eyes.crop_box: max(2 · max(w, h), 64 px)), состояние сети переносится непрерывно; глаз удаляется вместе с треком (потеря > 30 кадров) и сохраняется при возврате. Вход глаза — сетчатка-ламина, как у сигнатур стенда. Считывание (без изменений, как в [flyvis_fovea_motion_v1↗](obsidian://open?vault=ObsidianFlyVis&file=01%20%D0%9C%D1%83%D1%85%D0%B0%2F%D0%AD%D0%BA%D1%81%D0%BF%D0%B5%D1%80%D0%B8%D0%BC%D0%B5%D0%BD%D1%82%D1%8B%2Fflyvis_fovea_motion_v1), scripts/build_foveated_readout_cache.py): остаточный декодированный поток глаза (минус базовый после разгона), среднее по колонкам внутри прогнозной рамки, × сторона вырезки / размер ядра → px кадра, ось y вниз; δ = g · это среднее. Действие: только для потерянных треков, после прогноза Калмана перед первым сопоставлением, центр прогноза сдвигается на δ (скорость не меняется). Подавление: < 3 колонок внутри рамки — без поправки; |δ| ограничено половиной большей стороны рамки. Ведомые треки не поправляются (O1 без запаса). Движение изображения в глазу складывается из движения объекта и перемещения / изменения размера вырезки; считывание это не разделяет — ограничение, не проверенное заранее.

## Вопрос
Улучшает ли фовеальный глаз, сохраняемый при потере трека, HOTA стенда через поправку положения потерянных треков, и даёт ли пользу именно непрерывное состояние мухи?

## Гипотеза
Непрерывное состояние FlyVis на потерянном треке даёт поправку положения, которая возвращает часть потерянных треков к своим детекциям.

## Ожидалось (до прогона)
Варианты (одни детекции, один трекер стенда XYWHByteTrack 30 Гц, без сшивки): S0 — стенд (штатная муха: глаз удаляется при потере, поправки нет); P-carry — глаз сохраняется, состояние непрерывно; P-reinit — контроль: та же муха, тот же глаз и то же считывание, но в момент потери глаз заново разгоняется на текущем кадре в вырезке прогноза (состояние не переносится); DIS — ориентир: та же поправка из поля DIS (среднее поле в рамке минус перемещение вырезки за кадр). g подбирается для каждого варианта отдельно МНК на 20 видео train (фиксированный выбор, seed 0) по кадрам потерянных треков, где своя уверенная детекция в области глаза (цель — центр детекции минус центр прогноза; разметка — только для подбора, интерполяция как в [association_log_v1↗](obsidian://open?vault=ObsidianFlyVis&file=01%20%D0%9C%D1%83%D1%85%D0%B0%2F%D0%AD%D0%BA%D1%81%D0%BF%D0%B5%D1%80%D0%B8%D0%BC%D0%B5%D0%BD%D1%82%D1%8B%2Fassociation_log_v1)), при траекториях стенда (g = 0 в проходе подбора). Критерии (dev 35, HOTA по видео, бутстрэп 5000): К1 — P-carry − S0 > 0, ДИ > 0 (польза стенду относительно штатной мухи); К2 — P-carry − P-reinit > 0, ДИ > 0 (польза непрерывного состояния). Справочно: DIS − S0, P-carry − DIS, общий прирост, AssA, IDSw, ночь. К1 не выполнен — остановиться без переделки. К1 выполнен, К2 нет — польза от считывания глаза, а не от непрерывного состояния (так и записать). При К1 — отдельный шаг: проверка со сшивкой MASA. +0,471 оракула — не ожидаемый результат и не потолок. Цена — по короткой технической пробе до запуска; GPU — по согласованию.

## Условия
- **baseline:** S0 — стенд (штатная муха, глаз удаляется при потере)
- **variant:** P-carry; контроль P-reinit; ориентир DIS
- **dataset:** BDD100K MOT train_cache: 20 видео train (подбор g), dev 35 (критерии)

## Критерии приёмки (записаны до прогона)
- ⏳ Сверка: S0 = стенд без сшивки (HOTA 61,336); глаз ведомых треков в P-carry совпадает с глазом стенда до первой потери
- ⏳ К1: dev 35, HOTA P-carry − S0 по видео > 0, ДИ > 0
- ⏳ К2: dev 35, HOTA P-carry − P-reinit по видео > 0, ДИ > 0
