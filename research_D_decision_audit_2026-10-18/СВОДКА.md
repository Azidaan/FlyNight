# 1. Решение после исследования

Проверка литературы поддерживает исходное направление, но не обещает улучшение. Ближайшее действие — новый выход полезности внутри считывателя FlyVis при фиксированных центрах C_center и D_center. Следующий кандидат для обучения самой D — согласование ядра с применяемой моделью цели. Повторять прежние 100 эпох без изменения проверяемого механизма оснований нет.

Позиция до поиска: `01_ПОЗИЦИЯ_ДО_ПОИСКА.md`; её хеш и хеши семи опорных научных файлов сохранены в `baseline_manifest.json`. Источники и таблица R1–R6 после поиска: `02_ИСТОЧНИКИ_И_СРАВНЕНИЕ.md`. Это целевой обзор двенадцати первичных работ, не полный систематический обзор. Новых расчётов, обучения, HOTA и изменений научного кода при исследовании нет.

# 2. Что сохраняется из результатов

На dev35 D_center улучшила долю полезных центров относительно D_prior на +3,99 п.п., 95% ДИ [+1,17; +6,92]. Относительно R1_center разность +9,89 п.п., ДИ [+7,26; +12,56]. Но D_center − C_center равна −3,04 п.п., ДИ [−10,26; +1,51]: преимущество обученной D над штатной C не доказано. Это не доказательство равенства и не доказательство превосходства C. Источник: `runs/z13_target_center_dev_20261018/report.json`, `paired`.

Локализация стала лучше, надёжный выбор ответа пока не получен. Прежняя оценка присутствия при новых центрах не прошла основной критерий на train26 (`runs/z13_score_swap_20261018/report.json`). Нельзя подменять его более удобной долей отбора после просмотра данных. Эти результаты относятся к эпизодам; новые HOTA и польза стенду не измерены.

# 3. Что поиск изменил в рекомендации

Для обучения через фактически применяемое считывание найдено более прямое основание: DiMP, §4.1, таблица 2. Поэтому R3 имеет содержательную опору, но остаётся гипотезой для нашей D. [Первичный текст](https://arxiv.org/html/1904.07220v2).

Уточнение R2: нельзя ограничиться предсказанием геометрической точности, забыв, тот ли объект найден. Оценщик должен получать наблюдаемые признаки активности/сопоставления и обучаться на точном совместном событии полезности, включая известные неполезные поправки и отсутствие цели. Неизвестные исходы остаются неизвестными. Это адаптация принципов S3/S5/S6, а не утверждение, что готовая статья решила нашу задачу.

Критические статьи о FlyVis не дают основания объявлять обучение бесполезным. В частности, проверка Dhiman ограничена ранними шагами на простой задаче; её основная ценность для нас — устройство контролей. S10–S12 также не заменяют наши парные измерения.

# 4. Что делать дальше, по порядку

## 4.1. Первое действие: проверяемая полезность ответа

Сохранить центры нынешнего узла. Новая часть внутри считывателя должна оценивать событие из `scripts/z13_train.py`, `success`: цель присутствует, ошибка центра укладывается в прежний допустимый масштаб и ниже ошибки прогноза. Поиск считается прежним; меняется один узел, выбирающий применение найденного ответа.

Гипотезы о затруднении ранжированы так. Первая: нынешний балл не обучен на требуемое событие — подтверждено различием задач в коде. Вторая: доступных наблюдаемых признаков достаточно для нового оценщика — гипотеза. Третья: улучшение отбора даст улучшение HOTA — гипотеза, проверяемая только в замкнутом трекере. Ни первая формулировка, ни поиск литературы не устанавливают единственную причину провала нынешнего отбора.

Контроли: прежний балл на тех же центрах; новый оценщик на одной геометрии без активности; тот же оценщик с одинаковым бюджетом на D, C и R1. Геометрический контроль нужен потому, что ответ может объясняться лишь расстоянием до прогноза, масштабом и возрастом потери. Если добавление активности не помогает, это не результат модернизации FlyVis.

Сначала обучение и выбор на обучающих видео с разделением по видео; прогнозы для подгонки оценщика должны получаться без использования оценочных исходов. Для обучаемого ядра/считывателя нужны прогнозы вне тех видео, на которых подгонялись их параметры. Нельзя случайно поделить соседние кадры одного эпизода между обучением и оценкой. Карты ответа могут потребовать отдельного извлечения; стоимость не измерена, обещания «только готовый CPU» нет.

Критерий будущей проверки: больше полезных вмешательств при заранее согласованном ограничении известных неполезных вмешательств и учёте неизвестных; парное сравнение по видео с прежним баллом и контролем без активности. Если данных мало, итог — неопределённость. Численный допуск риска, единица его расчёта и бюджет требуют отдельного протокола до прогона. Это предложение; опыт сейчас не назначен и не запущен.

## 4.2. Второе действие: обучение ядра под новый узел

По коду D обучалась с пространственной классификацией, а теперь используется регрессия модели цели. Сначала нужен численно воспроизводящий дифференцируемый вариант (передающий ошибку обучения через считывание в ядро); затем парное сравнение при одном считывателе с фиксированным и обучаемым ядром. Это отдельная проверка. Новую функцию потерь для фона, историю, масштаб и длительность не менять одновременно. Превосходство над C обязательно для утверждения о пользе нашего обучения.

Если первое действие не даёт полезного отбора, вопрос второго решается по конкретной проверенной причине, а не автоматически объявляется бессмысленным. Иначе отказ от одной реализации снова превратится в необоснованный отказ от линии.

## 4.3. Дальнейшее применение в трекере

Только после заранее записанного допуска — измерение HOTA: исходный стенд, поправка без FlyVis, та же поправка с FlyVis. Повторно используемый dev не становится слепой проверкой от нового названия опыта; отложенные 75 видео остаются отдельной финальной ступенью. Работа с литературой не является разрешением на её запуск.

# 5. Сильнейшее возражение и граница решения

Возможно, полезную часть уже даёт штатная C с новым считывателем, а дальнейшая адаптация D переобучит ядро. Возможно и другое: новая оценка будет выбирать удобные случаи, но не улучшит итог трекера. Против этих версий нужны парные контроли; число найденных статей их не опровергает.

Исследование не изменяет сохранённые веса и измеренные результаты. Если оно обнаружит ошибку измерения, исправлению подлежит вывод с сохранением прежнего текста. При ухудшении новой версии опорная не заменяется. Ни одно из рассмотренных ограничений само по себе не опровергает уже измеренный прирост центрированного считывания.

Сводка к baseline (опорной версии): новых экспериментальных процентов нет. Для прежнего D_center относительно D_prior средняя повидео доля полезных центров выросла с 0,142989765 до 0,182908587, то есть на 27,92% относительно D_prior; первичный источник — `runs/z13_target_center_dev_20261018/report.json`, `summary.D_prior` / `summary.D_center`. Это не процент HOTA. Доля измеренного потолка не определена: сопоставимый потолок для нового правила применения не измерен.
