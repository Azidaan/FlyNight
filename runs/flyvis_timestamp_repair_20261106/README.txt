1. Что исправлено и где проходит граница

Добавлен отдельный исполняемый путь Б1 с учётом времени наблюдений: tracking/b1_timestamped.py. Он использует исходные ядро, считыватель и алгоритм сопоставления, но передаёт номера кадров через TimestampedB1Tracker → TimestampedResidualEngine → TimestampedBackbone. Обучение вызывает тот же TimestampedBackbone через forward_timestamped_residual. Это изменение полного модуля FlyVis и его включения в авторскую систему; топология нейронного ядра не изменяется.

Подтверждённый дефект старого пути: четыре перехода сохранённого примера uid=0 имеют номера [18,21,22,24,26], то есть интервалы [3,1,2,2] исходных кадров. В прежнем Б1 каждый переход занимал 1/30 с. Новый путь получает фактический FPS из метаданных видео, здесь 30,202929825289456, и интегрирует суммарно 0,2648749656499038 с вместо 0,13333333333333333 с. Эти числа независимо пересчитаны из исходного архива и метаданных в independent_validation.json; это длительность входа, а не измерение улучшения качества.

Формула времени зафиксирована в контрольной точке: frame_delta / actual_source_fps. FPS является входом конкретного видео, а не постоянным значением всех моделей. Фактические индивидуальные PTS видеокадров (временные отметки контейнера) здесь не доступны: используется уже сохранённый FPS. Подготовка начального состояния первым изображением сохраняет прежний fade-in; изменение его численной схемы не входит в исправление.

Внутри FlyVis промежуток делится на ceil(duration/0,02) шагов с dt=duration/count. Пропущенные изображения линейно интерполируются между уже полученными концами промежутка. Это не восстановление реально существовавших промежуточных изображений. Контроли без FlyVis B и R1 получают те же концы и один интерполированный шаг на исходный кадр. У них не заявляется непрерывная физическая динамика. Повтор одного frame ID при дополнении короткой истории не продвигает время; разное изображение с тем же ID отвергается.

2. Исторический путь и новые модели

tracking/b1_tracker_runtime.py:ResidualEngine, tracking/b1_learning.py:forward_residual, tracking/z13_readout.py:FlyBackbone и scripts/b1_residual_train_20261027.py сохраняются как исторический путь для воспроизведения прежних опытов. Его временная семантика известна как ошибочная при пропусках; для новых научных выводов о корректном времени использовать этот путь нельзя. Файлы не переписаны, прежние веса не переинтерпретированы. Точные SHA256 старых источников указаны в real_D_v2/protocol.json и проверены в independent_validation.json.

Новая схема имеет marker b1_observed_frame_time_v1 и полный словарь temporal_semantics. restore_timestamped_checkpoint и TimestampedResidualEngine отвергают старые контрольные точки без этого словаря и несовместимые варианты. Нельзя добавлять marker к старым весам вручную: новое время требует отдельного обучения и отдельного сравнения с контролями. Никакого автоматического перевода старых весов не выполнено.

В реальном исполнении использовать TimestampedB1Tracker с TimestampedResidualEngine. Этот трекер не принимает старый ResidualEngine. Вызовы begin(frame, image), update(detections), after() сохраняют прежний порядок, но frame должен быть исходным номером кадра и строго возрастать. Для нового видео reset() очищает собственные histories/eyes/previous/events и локальные часы/идентификаторы; общий сервер внешнего вида и банк глаз сбрасывает их владелец. Конструктор, update и reset сохраняют глобальный счётчик других трекеров.

3. Основной API обучения и исполнения

make_timestamped_modules(arm, device=..., estimator=..., neighbors=..., trainable=True) возвращает backbone, head. Для C/D нужен estimator на выбранном устройстве; для B нужны реальные соседи колонок глаза. C сохраняет замороженное ядро, D обучает прежние три группы параметров, B обучает контрольную сеть, R1 не имеет обучаемой основы. Начальное нулевое считывание сохраняет базовые вероятности точно.

load_timestamped_observation(ROOT, row, device) читает из одного архива и изображения, и номера кадров; проверяет привязку reference_frame/current_frame и запрещает выход за ROOT. tensors_for_row остаётся общим с прежним Б1. Вызов обучения:

    hexes, frames = load_timestamped_observation(ROOT, row, device)
    inputs = tensors_for_row(row, hexes, probability, device)
    updated, delta = forward_timestamped_residual(
        backbone, head, hexes, row, inputs,
        frame_numbers=frames, source_fps=video_fps,
        train_backbone=arm in ("D", "B"))
    loss = identity_objective(updated, delta, labels, inputs["real"])

Метки передаются только в identity_objective. Если loss=None, запрос не имеет известных реальных кандидатов и не даёт шага оптимизатора. Для D после обычного backward/optimizer.step вызывать backbone.backend.clamp(), как в прежнем обучении; группы ядра доступны через backbone.backend.param_groups(). Для сохранения использовать timestamped_checkpoint(backbone, head, cursor=..., optimizer=..., provenance=...); для продолжения restore_timestamped_checkpoint(..., optimizer=optimizer).

Для исполнения создать отдельные экземпляры модулей через ту же фабрику, затем TimestampedResidualEngine(backbone, head, checkpoint, source_fps=video_fps) и TimestampedB1Tracker(args, bank, geom, server, base, engine). Engine владеет переданными модулями и замораживает их; не передавать сюда объекты продолжающегося обучения. База, геометрия, сервер внешнего вида и детекции остаются обычными входами Б1. Новый класс является пригодной точкой подключения к настоящему get_dists, а не только отдельной функцией интерполяции.

Загрузчик проверяет обе части модели до копирования, включая переполнение при приведении float64 к float32, целочисленную геометрию B и курсор. Состояние оптимизатора предварительно загружается на приватную копию; проверяются конечность и формы стандартных моментов. При ошибке реальной загрузки восстанавливаются тензоры обеих моделей и state/param_groups оптимизатора. Проверка такой ошибки с пользовательским hook (обработчиком загрузки) включена в тесты.

5. Что результат не доказывает

Полное обучение новой модели, HOTA и польза для трекинга не измерены. Два шага служат только проверкой исправности вычислений и производных. diagnostic_checkpoint.pt помечен diagnostic_only; обычный engine его отвергает. Разрешение allow_diagnostic=True используется только для этой технической проверки и не превращает файл в обученную экспериментальную модель. Отношение новой HOTA к исходной и доля измеренного предела не вычисляются: обе величины здесь отсутствуют.

Для нового научного вывода нужен отдельно зарегистрированный запуск с корректными временными входами и одинаковыми наблюдениями у FlyVis и контролей B/R1. Исторические отрицательные результаты не переписаны и не объявлены недействительными на основании одного исправления времени.
