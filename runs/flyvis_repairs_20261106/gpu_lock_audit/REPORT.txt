1. Подтверждённые дефекты

Исходный tracking/gpu_lock.py продолжал защищённый участок, если CreateMutexW возвращал NULL. Нативная проверка без GPU создала объект Event с уникальным именем, затем запросила Mutex с тем же именем. Windows вернула ошибку 6; исходный код всё равно исполнил тело with. В исходном варианте также отсутствовал CloseHandle: после создания и удаления 100 свободных экземпляров число дескрипторов процесса выросло с 145 до 245 и осталось 245 после gc.collect(). Проверка самостоятельно закрыла свои 100 дескрипторов. Освобождение мьютекса чужим потоком тоже не сообщало об отказе. Первичные данные: before_report.json; исходный код: original_gpu_lock.py.

2. Исправление и договор

Проверяются результаты CreateMutexW, WaitForSingleObject, ReleaseMutex и CloseHandle. Отказ создания или захвата больше не допускает исполнение защищённого участка. Состояние владения учитывает поток, глубину повторного входа и ожидающих; небольшая локальная блокировка защищает это состояние. WAIT_ABANDONED остаётся успешным получением владения после смерти прежнего потока. Прежние имена мьютексов и вызовы from_env не изменены.

Выход из with освобождает владение, но сохраняет дескриптор для следующего кадра EyeBank. Явный close закрывает только свободный экземпляр; повторный close безопасен. Свободный объект автоматически закрывается при удалении. Закрытие занятого мьютекса или объекта с ожидающими потоками запрещено; неверное использование при удалении сообщает ResourceWarning и не закрывает потенциально используемый другим потоком дескриптор. Значение None и платформа вне Windows сохраняют прежний режим без блокировки.

3. Проверки

После исправления тот же нативный отказ создания завершился OSError до защищённого тела. У 100 объектов число дескрипторов временно выросло с 145 до 345, включая локальные блокировки Python, затем вернулось к 145 после удаления; дополнительное закрытие проверкой не требовалось. Освобождение чужим потоком завершилось RuntimeError. Первичные данные: after_report.json; source_sha256 5b488c82fc49d22957785089156d72507000782d661e1b8a0c1fbe2ef0e9f828.

tests_final.log: 13 passed in 1.09s. Проверены реальный конфликт имени с Event, повторные и вложенные входы, освобождение дескрипторов, отказ чужого потока, ожидание трёх потоков, восстановление после завершения владельца, явные отказы трёх операций Windows, повторный close, а также два отдельных дочерних процесса. Процесс с тем же уникальным именем ожидал освобождения родителем, процесс с другим уникальным именем прошёл независимо. Созданные проверками дочерние процессы завершены, все проверочные имена были уникальными. Исходные шесть адресных проверок дали 5 failed, 1 passed до исправления; tests_before.log сохранён.

Команда: .venv/Scripts/python.exe -m pytest tests/test_gpu_lock_lifecycle.py -q -p no:cacheprovider. Нативная проверка: .venv/Scripts/python.exe runs/flyvis_repairs_20261106/gpu_lock_audit/probe.py --report-name after_report.json. Для повторения выбирать новое имя отчёта, чтобы сохранить прежние свидетельства.

4. Граница результата

Проверены механизм Windows и собственные тестовые процессы, без импорта Torch и без обращения к GPU. Это не проверка CUDA, пропускной способности и научных метрик. Различные имена блокировок по-прежнему не координируются; автоматическое объединение имён не выполнялось. Инвентаризация 86 файлов вызова находится в native reports, отдельная независимая проверка вложенных вызовов рассматривает возможность взаимного ожидания родителя и дочернего процесса. Результат исправления не доказывает отсутствие такого ожидания во всех возможных внешних сценариях.
