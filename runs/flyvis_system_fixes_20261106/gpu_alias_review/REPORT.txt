1. Область проверки.

Независимая статическая проверка путей вызова GpuLock выполнена без GPU, без импорта рабочих модулей и без создания или захвата настоящих блокировок. scan_paths.py рекурсивно прочитал scripts/ и tracking/. inventory.json содержит 95 файлов с упоминанием блокировки или переменной среды, 86 вызовов конструктора и SHA256 каждого файла. assess_paths.py обнаружил 83 области with GpuLock и проверил прямые вызовы процессов, а также достижимость функций того же модуля. call_graph.json не содержит запуска процесса внутри такой области или достижимого из неё через именованные функции того же модуля. Это статическая проверка известных путей, а не доказательство для произвольного динамически подставленного кода.

2. Подтверждённая несовместимость имён.

29 вызовов задают Local\\DissertationSingleGpu, 54 задают flyvis_fovea_gpu, один условный вызов выбирает None либо flyvis_fovea_gpu, один задаёт FlyVis_z13_observed_memory_single_gpu, один получает имя из FOVEA_GPU_LOCK. В tracking/gpu_lock.py эти имена передаются CreateMutexW без преобразования. Разные имена обозначают разные объекты Windows и потому не обеспечивают взаимного исключения для одного GPU. Это установленное свойство программы и Windows API; одновременные научные процессы в этой проверке не запускались.

3. Родитель и дочернее задание.

15 файлов одновременно содержат GpuLock и вызовы subprocess. В candidate_reserve, candidates_night, distribution_pilot, distribution_quality и observed_memory блокировка находится в вычислительном worker/extract/compute, запуск и ожидание находятся в отдельном controller/control. В history_clock, region_assignment и spatial_set_readout блокировка находится в feature_worker, запуск фаз — в pipeline. В temporal_identity_features вызов subprocess относится к prepare и чтению git, блокировка — к worker. В spatial_hota_masa_price main выбирает worker либо запускает дочерний worker. В matched_pipeline, matched_stock_controls, val20_common, val20_common_authorized и val20_inputs child запускает отдельный --job и ждёт без GPU-блокировки; блокировку получает build_signature/build_masa/build_missing_masa/job в дочернем процессе. Все пути и строки сохранены в inventory.json. Отдельно просмотрены ветвления __main__ и функции child/worker пяти matched/val20 файлов.

run_fovea_jobs.py сам не захватывает GpuLock: потоки диспетчера запускают задания с FOVEA_GPU_LOCK=flyvis_fovea_gpu. Их threading.Lock защищает таблицу состояния диспетчера и не является GPU-мьютексом. build_z13_spatial_hota.py удаляет FOVEA_GPU_LOCK и держит внешний GpuLock вокруг build_video; внутренние блокировки отключены намеренно. Не обнаружено пути, в котором родитель удерживает этот GPU-мьютекс и ждёт дочернее GPU-задание, которому понадобится тот же объект. Не утверждается отсутствие любой возможной блокировки внутри сторонних библиотек.

4. Вложенное владение.

В matched/val20 build_signature внешний GpuLock охватывает build_fly_signatures.build_video. Внутри него EyeBank и обработчики Z13 используют bank.gpu_lock из from_env. Выполнение синхронное в том же потоке. Windows разрешает владельцу повторно захватить тот же мьютекс; каждый успешный захват требует отдельного ReleaseMutex. Текущий GpuLock с отдельным счётчиком глубины на экземпляр сохраняет это правило и при двух экземплярах с одинаковым именем. Отдельный threading.Lock для защиты метаданных не удерживается на время пользовательского тела with или WaitForSingleObject. Нового подтверждённого дефекта жизненного цикла в этом обзоре не выявлено.

5. Минимальное предложение, ещё не реализованное в этой проверке.

Преобразовать только три известных GPU-имени в одно существующее Local\\DissertationSingleGpu при создании GpuLock. Сохранить requested_name для диагностики и effective name для Windows при необходимости. None и пустая строка остаются отключением; произвольные пользовательские имена сохраняются как отдельные объекты. from_env без переменной не должен самовольно включать блокировку. Не приобретать несколько старых имён одновременно: единое каноническое имя решает проблему без нового порядка вложенных захватов. Для доказательства преобразования достаточно тестового подменённого Win32 API, который фиксирует CreateMutexW, и изолированных случайных тестовых имён при проверке рекурсивности. Рабочие имена в проверках не захватывать.

Изменение применится только к процессам, загрузившим новую версию модуля. Уже запущенные процессы со старым кодом продолжат использовать прежний объект. Local ограничен текущей сессией Windows; переход на Global или объединение произвольных имён не входит в это минимальное исправление. Общая блокировка координирует участвующие вызовы, но не создаёт защиту вокруг неохваченного GPU-кода.

6. Первичные источники.

Microsoft CreateMutexW: https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createmutexw — имя сопоставляется с существующим объектом, сравнение чувствительно к регистру, Local/Global задают пространство имён, NULL security attributes не разрешает наследование handle дочерним процессом.

Microsoft Mutex Objects: https://learn.microsoft.com/en-us/windows/win32/sync/mutex-objects — владение принадлежит потоку, повторный захват владельцем не блокируется, освобождение требуется на каждый захват.

Microsoft Kernel object namespaces: https://learn.microsoft.com/en-us/windows/win32/termserv/kernel-object-namespaces — клиентская сессия использует своё пространство по умолчанию; Local указывает его явно, Global имеет другую область действия.
