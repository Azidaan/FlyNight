# 🟢 Оракул удаления отдельных ложных жизней внутри готовых цепочек после MASA (dev): запас сверх удаления целых цепочек

↑ [[01 Муха/Темы/Прочее о мухе|Прочее о мухе]] · **Исход:** положительный · `life_filter_oracle_v1`

Разбор автора 09.10: проверить запас действия тоньше цепочки, прежде чем учить голову. Готовый выход «база + MASA» (dev, runs/chain_filter_rank/repro/dev) не пересчитывается — итоговые номера и связи сохраняются, сшивка не запускается, удаляются только рамки. Ступени: 1 — исходный; 2 — удалены полностью ложные цепочки; 3 — плюс полностью ложные жизни (фрагменты трекера до сшивки) внутри оставшихся цепочек; 4 — все ложные рамки (справочно). Жизни без учитываемых рамок — неизвестно, не удаляются. Правило «ложная» — как output_filter_oracle (IoU 0,5, венгерское по классу, crowd — игнор). Принадлежность рамок к жизням — по координатам строки трекера; проверка на 019efe88-bbc2a4ac: все рамки однозначно, ступень 1 = исходный HOTA 65,285. Только dev; разрешение ограничено этим расчётом и отчётом (обучение головы и GPU — отдельный шаг). scripts/life_filter_oracle.py.

## Вопрос
Сколько HOTA даёт сверх удаления целых ложных цепочек удаление ложных жизней внутри смешанных цепочек (оракул)?

## Гипотеза
Заметная часть запаса между ступенями 2 и 4 (+1,5 HOTA на test) сидит в целиком ложных жизнях внутри смешанных цепочек.

## Ожидалось (до прогона)
Критерий перехода (до прогона): ступень 3 − ступень 2 по HOTA на dev — средняя по видео > 0 с ДИ > 0 (бутстрэп 5000) И общий прирост ≥ +0,3 HOTA (≈ 0,5 % HOTA выхода; порог величины задан агентом, автор может пересмотреть до использования). Иначе эту реализацию действия не развиваем. Оракул не доказывает достижимость головой и вклад FlyVis.

## Интерпретация
Запас у удаления отдельных жизней внутри готовых цепочек есть, но небольшой: +0.326 HOTA сверх удаления целых цепочек (по видео +0,311, ДИ выше 0, 29/35), ночью больше (+0,431, ДИ выше 0, 12/15). Прирост в DetA и AssA одновременно, найденные объекты не теряются (оракул удаляет только ложные). Это 21 % остатка между удалением цепочек и всех ложных рамок; остальные 79 % — ложные рамки внутри смешанных жизней, их удалением целых жизней не достать. Порог величины +0,3 выполнен впритык. Оракул знает разметку: достижимость головой и вклад FlyVis не проверены. Найдена ошибка 09.10 (разбор автора): в signatures.npz один номер трекера встречается в нескольких записях жизней (трек потерян и вернулся с прежним номером; dev — 49 652 записи при 41 304 уникальных номерах, train — 196 216 при 159 592). Рамки выхода относились к жизни по номеру, а не по записи и интервалу кадров: метки и потери считались для объединения всех жизней номера (pos = {tid: i} оставлял последнюю запись), признаки life_features (уверенность, число строк) смешивали жизни номера, удаление шло по номеру. Пример: 019efe88-bbc2a4ac, номер 8 — жизни 0–129 (3 верных, 5 ложных) и 141–221 (0 верных, 8 ложных) получили общую метку 0. Ограничение вывода: +0,33 HOTA — эффект удаления групп по исходному номеру трекера, не потолок удаления отдельных непрерывных жизней; пересчитывается в [life_filter_oracle_v2↗](obsidian://open?vault=ObsidianFlyVis&file=01%20%D0%9C%D1%83%D1%85%D0%B0%2F%D0%AD%D0%BA%D1%81%D0%BF%D0%B5%D1%80%D0%B8%D0%BC%D0%B5%D0%BD%D1%82%D1%8B%2Flife_filter_oracle_v2).

## Решение
Критерий перехода выполнен (оба пункта), но прирост на грани порога. Следующий шаг — по решению автора (обучение новой головы — отдельное разрешение): голова отдельных жизней (цель «жизнь полностью ложная», жизни без учитываемых рамок — неизвестно) на жизнях train 130, без мухи и с мухой при одинаковом протоколе, порог с бюджетом потерь на dev. Ожидаемый реализуемый прирост мал (оракул +0,33 на dev; прежние фильтры брали ≈ 10 % своего оракула) — стоит взвесить против других путей.

## Нельзя заявлять
Это оракул по разметке на dev: запас действия, не достижимый результат; вклад FlyVis не проверялся. Правило IoU 0,5 — диагностическое. Числа получены с ошибкой идентификации жизней (см. interpretation) — как вердикт для отдельных жизней не использовать.
